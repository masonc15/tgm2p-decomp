# Shiftable build

2026-10-16. `make shiftable` relinks the matching build's objects with every
code and data address written as a symbol and no fixed-address asserts, so
code and data can grow, shrink or move. It is a second, independent link of
the same sources: the matching build (`make check`) is untouched and still
places and asserts every object at its original address.

Proof, on this commit:

- With no padding the image is byte-identical to the original program
  (`sha1 c84cf538962ddbb377290301d76d75d8b542e5a2`; `make shiftable` fails
  otherwise).
- With 1,024 bytes inserted mid-`.text` (before `src/playfield_1913c.c` at
  ROM `0x1913c`) and 256 bytes mid-ROM-data (before the data block at
  `0x72194`), the game runs in MAME frame-identically to the original over a
  12,000-frame attract run and a 24,000-frame scripted gameplay replay: all
  360 screen-hash checkpoints match (96 and 237 distinct screens).

```
$ make shiftable SHIFT_PAD="0x1913c:1024 0x72194:256"
$ tools/replay_check.sh --nodrc build/shiftable-pad/tgm2p.bin
attract: 12000 frames, 120 checkpoints every 100 frames (96 distinct screens): identical
gameplay: 24000 frames, 240 checkpoints every 100 frames (237 distinct screens): identical
```

## Layout model

The boot code's copy table at `0x313fc` describes the memory map: `.text`
(ROM `0x780`–`0x313fc`) runs from RAM `0x06000000`; initialized RAM data
(ROM `0x3141c`–`0x36301`) is copied to the RAM right after it, `0x06030c7c`;
BSS from `0x06060000` is cleared; ROM data from `0x36304` is read in place.
The last 0x4ff01 bytes of the ROM, from `0xb00ff`, only repeat the 32 KB
before them and nothing references them; the shiftable build shortens this
filler by the total padding so the image stays 1 MB.

Every byte belongs to a unit: the vector table, each `splits.txt` segment,
the RAM data image, ROM data and the filler. Each unit has a global start
symbol `U_<rom>`; an address inside it is `U_<rom>+offset`. Units in `.text`
and `.data` get the RAM address, and `U_<rom>_lma` names their ROM copy. The
copy table itself is generated by the linker script from `LOADADDR`, `ADDR`
and `SIZEOF`, so the boot code copies whatever size the code has become.

| Unit kind | How it is linked |
|---|---|
| `asm` | regenerated from the ROM with labels for its own branches, pool loads and SHC `braf` switch tables (label differences); address-holding pool words become `.4byte U_xxxxxx+off` |
| `c` | the SHC object from `build/obj`, unchanged; its undefined `f_`/`d_`/`g_` and `symbols.txt` names are `PROVIDE`d as unit symbols |
| `c-prefix`, `c-range` | the retained SHC bytes repackaged from the context object with its relocations re-expressed (SHC's `R_SH_DIR32` is partial-in-place: the addend is the word in the section plus `r_addend`) |
| data | the vector table, RAM data image and ROM data as bytes, with every word classified as a pointer written as `.4byte` |
| copy table | `LONG()` expressions in the linker script |

GNU as for SH relocates no pc-relative instruction whose target is in another
object (`bsr`, `bra`, `bt`, `mov.l @(disp,pc)` to an external label all fail
to assemble), and a C source that writes an address as an integer, such as
`(struct frame *)0xa7130` or `#define HDR (*(struct frame ***)0x2004002c)`,
compiles to an unrelocated pool word. Both become fixups: each names its
location and its target by unit symbol, and `shiftable.py` applies them to the
linked image from the ELF symbol table, refusing any displacement out of
range. At zero shift every fixup reproduces the original word.

Current counts: 226 units; 968 pool pointers in asm units (583 into code, 209
into RAM data, 176 into ROM data); 85 literal addresses in C pools; 1,127
pointer words in data (178 code pointers, 152 RAM-data pointers, 797 ROM-data
pointers); 618 fixups (570 cross-object pc-relative instructions, 48 C
literal words). A unit that starts 2 mod 4 keeps its own pool loads as raw
halfwords, since gas computes pool alignment from the section start; padding
is always a multiple of 4, so those relative loads cannot change.

## Which words are addresses

Code pools. RAM addresses (code, RAM data) and cache-through ROM addresses
(`0x2004002c`, the header pointer) are always addresses. A value inside the
ROM copy of the RAM data (`0x3141c`–`0x36301`) never is: the game reads that
copy only through the copy table, and the two pool words there hold 216,000,
the frames in an hour, in the play-time screen (`0xd0ec`, `0xd268`). A plain
ROM-data value is an address unless it is integer-shaped: a multiple of 0x1000 (the
field flags `0x40000`, `0x50000`, `0x80000`), a mask (`0x7ffff`), or a packed
pair of small shorts (`0x000b0009`). Calibration: of the 145 ROM-data words
the linked C objects relocate, none is integer-shaped; of the 113
unrelocated ROM-range words in C pools, the 12 integer-shaped ones are the
flag and mask values `0x40000`, `0x50000`, `0x58000`, `0x70000` and
`0x80000` (`o->mask & 0x70000`, `p->l308 |= 0x50000`), and the other 101 are
the addresses the sources write as casts.

Data. Shape alone is not enough there. The 12-byte sprite frame records at
`0xa5000`+ pack `dx:dy` into words like `0x00080008`; the font metrics table
in RAM data at `0x337f8` holds `(w, h)` pairs like `0x00070007`; palettes
hold colours such as `0x00081400` (6-bit R, G, B, low byte zero). All of them
look like ROM-data pointers, and the first padded test drew the boot screen's
text with most glyphs pushed off screen. So data words are classified from
run-time evidence first:

```
REPLAY_READS_SKIP_BOOT=1 REPLAY_READ_RANGES=313fc-fffff,6030c7c-6035b63 \
  tools/replay_check.sh --reads build/prog.bin build/prog.bin
python tools/shiftable.py classify build/replay/ref-attract/reads.txt build/replay/ref-gameplay/reads.txt
```

The replay script logs every read of ROM data and RAM data with its width,
ignores reads by the boot block (its RAM test and copy/checksum loops read
every byte), and remembers each 32-bit read of an address-like value for the
next 16 reads; a read landing within 0x200 bytes after the value marks the
source word as followed. `classify` writes `config/shiftable_pointers.json`
(addresses only): 110 words read and followed, 51 read whose target is read,
6 code pointers to function entries, and 53 words read only at 8 or 16 bits,
which are fields and not pointers. Words the replays never touch fall back to
static rules: a candidate that is not integer-shaped (now including the
colour shape) is a pointer when it sits next to another such candidate, and
any candidate is one when its target is a function entry, an address the
code loads, or the target of another pointer (the ROM header at `0x40000` is
such a directory). This keeps strided singles out: they are what frame
records look like.

The evidence covers what the attract and gameplay replays exercise. Data
used only by other modes is classified by the static rules and is not proven
by this replay; one example is the header word `0x40020` (`0x00060090`, which
probably points just past the `PALETTE ` tag at `0x60088`), left as an
integer because no run reads it. The rules run on the data units as they
are in the original, before padding splits one: two frame pointers at
`0xacdfc` and `0xace34`, found through another pointer's target, were lost
when `0x72194` split their unit, and stayed unmoved in the first padded
images. The 216,000 constant was also moved by 1,024 in those images. The
replays reach neither, and both are fixed.

## Timing: the game's randomness counts idle loops

The first `.text`-padded builds matched the original in attract mode but
diverged in gameplay after about 1,600 frames, with every data read pointing
where it should. The frame wait in `f_2b4e8` spins `while (g_6060030 == 0)
g_606000c++;` and the system random `f_2beca` multiplies its state by
`g_606000c`. A larger `.text` makes the boot checksum and copy loops run
longer (about 0.42 idle spins per added byte), so the game starts at a
different phase of the video frame and the idle count, hence the piece
sequence, changes. MAME is deterministic, but that makes the replay sensitive
to the boot duration, not just to correctness.

Per-frame idle counts against the original, `.text` padding at `0x1913c`,
first 200 frames:

| Padding (bytes) | 4 | 16–128 | 256 | 512 | 1024 | 2048 | 4096 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Frames whose idle count differs | 0 | 53 | 30 | 53 | 1 | 1 | 53 |

With 1,024 or 2,048 bytes only the first frame after boot differs and the
phase re-locks exactly, so the randomness and the whole run match; with 256
bytes the residual phase changes the idle count by one in later frames and
gameplay diverges. ROM-data padding is outside the boot checksum and the
copies, so any amount works there. A shiftable build that changes the code's
size therefore changes the game's random sequence unless the boot length
lands on a phase-equivalent size; that is a property of the original
program, not of the link.

## Debugging tools

`tools/replay_check.sh` runs both images under the same scripted inputs and
compares screen hashes (FNV-1a over MAME's pixel buffer) at checkpoints. The
reference's hashes are cached in `build/replay-cache`, keyed by its image,
`replay.lua` and the run settings.
`--reads` (with `REPLAY_READ_RANGES`, `REPLAY_READS_FROM`/`_UNTIL`,
`REPLAY_READS_SKIP_BOOT`, `REPLAY_READS_PC`) logs reads, followed pointers
and per-frame read counts, and `shiftable.py mapreads` maps a padded image's
reads back to original addresses through the layout: a missed pointer shows
up as reads exactly one padding size off. `REPLAY_TRACE=FRAME:FILE` writes
MAME's instruction trace with registers for one frame (needs `mame -debug
-debugger none`), which found the remaining value-level differences: an asm
segment loading a frame address from a C unit's pool, and the header
pointers written as cache-through literals in C.

## Use

```
make shiftable                                   # zero shift; fails unless identical
make shiftable SHIFT_PAD="0xADDR:N ..."          # writes build/shiftable-pad/tgm2p.bin
tools/replay_check.sh [--nodrc] IMAGE            # attract 12000 + gameplay 24000 frames
SHIFTABLE_TESTS=1 python -m unittest tools/test_shiftable.py
```

`.text` padding goes before an existing segment; ROM-data padding at any
4-aligned address in `[0x3141c, 0xb00ff)`. Padding in `.text` is filled with
`nop`, so a function that falls into the next one still works. Both MAME's
recompiler and its interpreter (`--nodrc`) reproduce the proof; reads can
only be logged under the interpreter, since the recompiler reaches RAM
through direct pointers that bypass memory taps.
