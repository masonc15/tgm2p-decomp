# Mod build: the game linked from source

2026-11-17, phrixus. `make mod` links the program from its C sources as they
compile now, so the code can be changed and can grow. [MODDING.md](../MODDING.md)
is the user's guide; this note records how it works and what was verified.
The matching build is not involved: `make check`, `splits.txt` and the
coverage figures are unchanged, and nothing here counts as matching coverage.

## Why the shiftable build was not enough

The [shiftable build](2026-10-16-shiftable-build.md) already relinks the image
with every address symbolic, and proves it by reproducing the ROM at zero
shift. But it places matching C by the original's byte offsets. A `c` unit's
unrelocated address literals are found at their ROM offsets, and a `c-prefix`
or `c-range` unit is the byte range that the matching proof retained from its
context object. Both hold only while the source still compiles to the original
bytes, so padding could move code but an edit could not change it.

## Source units

`tools/shiftable.py build --source` treats every `c`, `c-prefix` and `c-range`
unit as a source unit (`tools/srcunit.py`). It compiles the source with the
pinned SHC and works only from the object the compiler produced:

The functions a unit owns are found by name: `f_<rom offset>`, or one of the
28 other names in `config/function_names.txt` (`main_loop`, `draw_text`,
`irq_vblank` and so on; `tools/shiftable.py names` writes the file from the
matching ELF and a test keeps it current). A file that one unit owns is linked
whole. A context source is cut: the unit takes its own functions and leaves
the copies of functions that other units own.

The cut is written as an assembly package. Relocated words keep their symbol.
A pool word that holds an address as a bare number becomes a symbol
expression, by the rule below. A pool load that reaches past the cut gets a
local copy of the word at the end of the unit, and a `bsr` that leaves the cut
becomes a fixup against the target's name. SHC shares pools and emits `bsr`
between the functions of one file, so both happen often: the unmodified game
needs 339 fixups and grows by 1,228 bytes of pool copies. `.rodata` comes
along, and for a whole file `.data` and `.bss` too.

SHC emits no symbol for a `static` function. A helper is found by the call or
the pointer that reaches it, decoded like the rest, and when it sits directly
ahead of the unit's first function the cut grows to take it in.

References from everything else follow the names. A reference into a source
unit that is not a function entry stops the build, with two exceptions that
stay numbers and are listed in `layout.json` (`dropped_pointers`). One is a
word in a pool that only replaced code loaded. The other is a data word:
compiled C has no interior that data could point to, so such a word is a
number the pointer rule mistook. There are eight, all in the sprite frame
records around `0xa703c`, `0xa80bc` and `0xaf030` (`0x06019790`,
`0x06019794`, `0x06019798`, `0x06019cce`, all inside `f_19d68`). The plain
shiftable build treats those eight as pointers and moves them with padding.
The replays do not show a difference from it, but they are not pointers, and
the pointer rule should learn the same fact.

## Numbers and addresses

A constant in compiled C is a bare pool word, so `(struct frame *)0xa7130` and
`300000` look alike. The matching sources write addresses as integers, and
those have to move. The source build takes a constant as an address only when
the original program loads that same value from a literal pool somewhere,
which is every address the game already uses. Any other value that merely
falls in an address range stays a number and is reported as a note (`300000`
is `0x493e0`, inside the ROM data). In new files and in `src/nonmatching/`
an address the game uses still has to be written as a symbol, as before.

## New code and variables

With `--mod DIR` a C file under `DIR` replaces the file of the same path, and
a file with no counterpart is new. New code is linked after the game's code.
Initialized variables go ahead of the game's own in the RAM data image, which
keeps that image's alignment and odd end. Variables without initial values go
into a new `.bss` at `0x060b19b4`, where the game's own end, and the copy
table's clear range grows to cover them. The stack comes down from
`0x060d0000`; the link fails if new variables come within 64 KB of it, or if
code and data reach the game's variables at `0x06060000`.

`tools/mod.py build` adds the non-matching units (accepted and staged), splits
the image into `2b.u21` and `1b.u22`, and links the other ROMs next to them.

## A missed frame is read from the frame counter

The pinned replay's condition is that no frame is missed. It was tested as "a
frame in which the candidate ran no idle loops while the original did". On
phrixus the 40-unit build fails that test in three attract frames (2,910,
6,170, 7,955), where the original logs one loop and the candidate none, with
identical screens. The padding-only build fails it too, in one frame, and it
runs the original's own instructions.

The cause is in the frame wait. `f_2b4e8` counts loops while the interrupt
acknowledge is pending as well as while it waits for vertical blank. In a
frame where the game starts several frames of blocking work it logs exactly
one such loop, and that loop lands on either side of the MAME frame boundary.
A count of zero there says nothing about frame time.

`replay.lua` now also records the game's own frame counter, `g_6065644`, as
each MAME frame ends. `f_2b4e8` increments it once per completed wait, so
code that overruns the frame time makes it fall behind the original's and
stay behind. `tools/idle_report.py frames` compares the two, `report` counts
a unit's missed frames from the slips, and `replay_check.sh --pin-idle` fails
on a slip instead of on a zero. In every build of the table the counter is
identical to the original's over all 11,989 and 23,989 compared frames.

This changes how the acceptance condition is measured, not the condition, so
the units below were first only staged, in a list that just the mod build
linked. (The 41-unit image of 2026-10-16 had no zero-idle frame in the cloud
session's run; it was a different image.) "Decisions" below has the outcome.

## The units the replays execute

rule. `f_5b80` needed `difftest-steps: f_5b80=1000000000`. Its row-collapse
loop is long on a random field height, width and row mask, not endless: input
`3/me4.1=20` returns after 52M steps and `3/me4.1=fd` after 432M, in the
original too, and all 500 trials complete at the larger limit.

`checksum_30880.c` (the ROM check, `0x30880`-`0x30a44`) and three of the four
settings units pass as well, after one correction to the harness (next
section). The replays never execute them, so the rule for them is the strict

`settings_d394.c` (`0xd394`-`0xe39c`, the code-entry, test and option menus)
failed at first. Three of its five functions pass. `f_d394` and `f_dbe8` got a
DIFFERENT verdict, each on an input no real run can produce, where the
original's behaviour depends on where its own frame and code sit:

- `f_d394`, input 59. The cursor column is set from `f_2beca(5)`, which
  returns a value below 5 in the game (`... % n`, `src/f_2bc64.c`). The
  harness stubs the call, and call #78605 returns -11. `tab[-11]++` then
  writes ahead of the ten-byte digit array, into the frame, and the
  original's frame is laid out differently from the candidate's. With that
  one result set to 3 (`--trace 59/c78605=3`) the two sides agree over all
  147,368 events up to the step limit.
- `f_dbe8`, input 136. `g_606006c[k].b1c = 64` uses the sprite slot that
  `f_2bf58` returned. Call #27529 returns `0x0612eb58`, slot -5,288 as a
  short, and the write lands at `0x0600d688`, in the original function's own
  literal pool: its next load of `g_6032f84` reads `0x40032f84`. The
  candidate's pool is somewhere else. With that result set to 1 the two
  sides agree up to the step limit.

Both are limits of testing with unconstrained stub results, not differences
between the two functions on valid inputs, but the acceptance rule had no
place for that judgement. "Decisions" below gives it one.

## A step limit hit inside a call was miscounted

`nonmatching_check.py` decides that a side hit the step limit when its step
count is above the limit. `sh2emu.py` reported `limit + 1` when the limit was
hit between calls, but `limit` when it was hit inside a stubbed call: the
stub's count was overwritten on the way out by the run loop's own, one behind.
A trial in which the two sides hit the limit in different places then read as
"only the original hit the step limit". The menu loops call something every
few instructions, so `f_a226`, `f_b3c0`, `f_be28`, `f_c21a` and `f_cac8` all
failed that way (138 of `f_a226`'s 500 trials were `2000001/2000000`). The
miscount could only fail a function, never pass one: a side that really
returns does so below the limit. `CPU.run` now keeps the larger count, and
`test_difftest.py` has the case.

## Decisions

Two things were open at this point: whether the frame counter is the
missed-frame test, and whether a stub may be held to its callee's result
range. Colin left both to the session's judgement on 2026-11-17. Both are
yes, for these reasons.

The frame counter is the test. All four frame drivers in
`src/frame_2b4e8.c` (`f_2b4e8`, `f_2b64a`, `f_2b816`, `f_2ba08`) increment
`g_6065644` once per completed wait, so a frame the candidate misses puts
its counter one behind the original's for the rest of the run, whichever
driver was waiting. A zero idle count does not measure that: the
padding-only build has one, running nothing but the original's
instructions.

A stub may be held to a range, when the callee's code proves the range.
`difftest.py --returns NAME=LO..HI` keeps the stubbed results of calls to
NAME inside it: a result already inside stays, and any other is mapped in by
the call's hash, the same on both sides. A source asks for it with
`/* difftest-returns f_x: f_y=LO..HI (why: ...) */`, per checked function,
and `nonmatching_check.py` refuses the line without its reason and prints
the range with the result. Two are in use, both in `settings_d394.c`:
`f_2beca=0..4` for `f_d394`, whose only call is `f_2beca(5)` (the function
ends in `% n`), and `f_2bf58=0..63` for `f_dbe8` (it returns a slot of the
64-record sprite table from the free list, `src/gfx_2bf58.c`). The risk is
a range that is wider in the real game than the one written down, which
would hide a difference outside it; that is why the reason is required and
names the code.

With those, the remaining 27 units are accepted, 35,402 bytes, which makes
45 units and 58,956 bytes of unresolved assembly, and
`splits_nonmatching_staged.txt` is gone:

- the 26 units the replays execute (31,298 bytes, 40 functions), with the
  evidence above and the pinned replay of the image `make shiftable
  NONMATCHING=1` now builds (`60f22cbe`): 360 checkpoints identical, frame
  counter identical, no frame missed, and no unit's frames missed in the
  per-unit report;
- `settings_d394.c` (4,104 bytes): all five functions pass under the
  non-returning rule, `f_d394` with 174 and `f_dbe8` with 45 random trials
  returning. The replays never execute it, and the 19-unit image with it
  (`bd8ad056`) passes the strict replay unpinned.

`tools/nonmatching_check.py` on the whole list: 77/77 functions.

What is still assembly after this is the boot code at `0x400`-`0x780`, three
literal pool tails that hold no instructions (`0xb39a`, `0xbddc`, `0x225fa`)
and the SHC runtime helpers at `0x30d40`-`0x3127c` and `0x312ba`-`0x313e4`
(the exempt ranges of `RUNTIME_EXCEPTIONS.md`).
